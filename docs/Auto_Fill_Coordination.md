# 桶体自动上水协同说明

## 1. 职责

桶体不实现第二套自动上水状态机。Bucket 只负责：

1. 收到透传模式 B2 后关闭桶体本地恒温，先确认基站已接收当前水位和温度，再转发 B2。
2. 继续用现有 frame[5] 和 frame[6] 上报整数水位、整数温度。
3. 根据基站 frame[23] 和 frame[28] 协同桶内循环。
4. 自动上水期间阻止 A2 启动桶体本地加热。
5. 基站状态退出或通信超时时清理自动上水循环。

协议长度和字段编码不变，不增加快速水位通道。

## 2. B2有序启动

只有链路模式为透传模式时，桶体才置自动上水活动标志。收到 B2 后执行：

- `Temp_Enable(0)`，关闭桶体本地加热。
- 关闭遗留的排水或循环模式，避免一边进水一边排水。
- 保存完整 B2，但暂不发送。
- 生成 `frame[3]=0x00` 的前置实时帧，写入当前水位、温度和本次令牌后发送基站。
- 匹配到基站回显的水位、温度和令牌后，才把保存的 B2 发给基站。
- 桶体主状态保持运行。

前置帧和 B2 使用不同令牌，防止旧的周期状态误认为本次 B2 结果。令牌借用
Bucket 到 Base 这一跳中基站不解析的桶体透传字段；Linux 状态帧仍由本地真实
数据重新构造，因此上位协议字段含义不变。

UART任务仍先处理已缓存的基站帧，再处理Linux命令。前置实时帧确认和B2结果
各有独立3秒等待窗口。重复B2会替换尚未转发的旧目标，并重新执行相同握手，
但不会重置Base内部自动上水总超时或5秒预通水。
## 3. 桶内循环门控

同时满足以下条件才允许因自动上水开启桶内循环：

| 条件 | 判断 |
| --- | --- |
| 基站正在自动上水 | frame[23] == 0x04 |
| 基站请求桶内循环 | frame[28] != 0 |
| 桶体水位传感器正常 | Sensor_IsWaterSensorOk() != 0 |
| 桶内安全水量 | Sensor_GetWaterLiters() >= 1.0f |

这里直接使用桶体本地浮点水量，而不是协议整数水位，避免实际约0.5 L经过
取整后被误判为1 L。最近一次frame[28]请求会保存，UART任务每50 ms重算
循环条件，因此水量刚跨过1.0 L即可响应，不必等待下一帧基站状态。

自动上水活动期间，水量低于1.0 L或传感器无效时，无论UV是否开启都立即
停止循环；自动上水结束后，也只有水位仍安全时才恢复UV循环，否则保持OFF。

## 4. A2与UV

- 自动上水活动期间收到 A2，桶体保持 Temp_Enable(0)，不启动本地加热。
- UV 在自动上水期间请求循环时，同样要通过本地1.0 L安全门控。
- UV 关闭后，如果基站仍请求自动上水循环，循环所有权交还自动上水流程。

这样可以避免基站2000 W即热模块和桶体加热模块同时工作，导致温度模型失效。

## 5. 结束与通信异常

以下情况清除自动上水跟踪：

- 已确认后基站状态离开0x04，包括完成、故障或切换其他模式。
- 前置实时帧3秒未确认、B2转发后3秒未返回匹配结果，或确认后基站超过3秒不在线。
- Linux主控超过5秒无合法帧。
- 收到 A0、A1、A7、A8、A9、C0。
- 收到其他基站模式命令或 B4 调试排水。

清理时只关闭由自动上水拥有的循环；UV仍开启时也必须水位安全才恢复循环。
超时、明确拒绝、完成或故障退出时，桶体主状态会依据恒温、UV、按摩电机和
定时器的实际状态恢复为运行或待机，而不是一直保留自动上水的运行状态。

## 6. 联调检查

| 场景 | 预期 |
| --- | --- |
| B2刚收到、前置实时帧尚未确认 | B2暂不转发，本地加热关，循环关 |
| 前置确认后B2已转发、尚无匹配结果 | 忽略旧状态，循环关 |
| 0x04且frame[28]=1，水量0.9 L | 循环关 |
| 0x04且frame[28]=1，水量1.0 L且传感器正常 | 循环开 |
| 0x04期间发送A2 | 桶体加热仍关闭 |
| 水位传感器无效 | 自动上水循环关闭 |
| 基站状态变0x05或0x06 | 清理自动上水标志和其拥有的循环 |
| 基站断开超过3秒 | 清理标志和其拥有的循环 |
| UV仍开启时自动上水完成 | 水位安全则保留循环，否则保持OFF |

状态上报仍使用原30字节协议，frame[5]、frame[6] 和 frame[16..28] 的含义不变。
令牌仅存在于Bucket到Base的内部透传帧，不能作为新的产品协议字段使用。
